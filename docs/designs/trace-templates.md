# Design: Trace Templates for Terminal Function Arming

## Problem Statement

In the Terminal tab (`#/terminal`), tracing a flow means picking a handful of top-level functions to arm for I/O inspection out of the whole-project catalog. Today that selection is one unnamed, flat set (browser `localStorage`, `frontend/src/lib/store.ts:25`) — it isn't scoped to any particular flow, and every time you come back to inspect the same area of code you re-find and re-pick the same functions from the catalog modal by hand. There's no way to name "these are the 6 functions I care about for the checkout flow" and get them all armed again in one click.

## What Makes This Cool

This turns one-off arm-selections into reusable **Trace Templates** you build up over time as you learn your own codebase — a personal library of "here's the interesting slice of this flow." And because it's exposed through the `brain-telemetry` MCP server too, Claude can save a template mid-debugging-session ("I armed these 6 functions to find the bug") and you can replay that exact instrumentation later with one click, without re-deriving what Claude was looking at.

## Constraints

- No database anywhere in this repo (`grep -rl "sqlite3\|sqlalchemy"` → no hits). Persistence follows the existing house style: a small JSON file per project, atomic write. (`backend/analysis/service.py:260-295` is the template for this — `.cache/routes-{sha1(project_path)[:12]}.json`, versioned, `.tmp` + `path.replace()`.)
- Function identity is the string `module:QualName` everywhere (`backend/api/viewer.py:290-302`, `backend/analysis/models.py:17-19`) — stable across backend restarts, but **not** through a rename or a move to another module. There is no persistent identity beyond the name path.
- Armed state (`TelemetryHub.selection`, `backend/api/viewer.py:55-67`) is a single in-memory, process-wide singleton — not per-session, not persisted today (`backend/state.py:1-5`: "No persistence, no caching layer beyond this — deliberately simple"). Templates only need to *populate* that singleton via the existing selection pipeline; they don't change its runtime model.
- The Terminal catalog scanner (`backend/scanner/ast_parser.py:134`) only walks `tree.body` — top-level functions and class methods, never nested closures. So "top-level, not deep" is already how the catalog is built; templates just need to remember *which* of those you picked.
- Two pieces of relevant logic already exist and should be reused, not reinvented:
  - `CatalogPane.tsx:33,124-138` already flags an armed id with no catalog match (`missing` / `armed-error` styling, tooltip "not found in the current scan — Rescan or remove").
  - `backend/mcp_server.py:145-151` already does fuzzy rename-suggestion for unresolved ids via `difflib.get_close_matches(f, known, n=3, cutoff=0.5)` when `arm_functions()` is called with an id that no longer resolves.
- The Terminal catalog already stays live: `AnalysisService`'s `watchfiles` watcher (`backend/analysis/service.py:180`, 800ms debounce) triggers `ExplorerState.rescan()` (`backend/app.py:40`) on every `.py` edit, so a fresh catalog is available to diff templates against without a new watcher.
- Two independent actors can write the templates file: the web UI and Claude via the MCP tools, potentially near-simultaneously. `AnalysisService`'s cache pattern is written by one background refresh cycle at a time, not by concurrent request handlers doing read-modify-write — the template store needs its own serialization (see Recommended Approach).

## Premises

1. The pain is real: today's arm-list is one unnamed flat set, not scoped to anything, so every context switch means re-picking from scratch. — confirmed
2. A JSON-file-per-project store, same pattern as the existing Routes/Lineage cache, is sufficient — no DB needed. — confirmed
3. "Flag if a saved function was removed" should reuse the fuzzy-rename-matching that already exists in `mcp_server.py`'s `arm_functions`, not something new. — confirmed

## Approaches Considered

### Approach A: Named templates (chosen, refined below)
Backend JSON-file store of named templates, each a flat list of `{function_id, deep}`. New CRUD + apply endpoints reuse the existing selection/apply pipeline. Frontend gets a "save current selection as template" action and a one-click template picker. Missing-function badges reuse existing styling.
- Rejected-in-original-form note: initial framing scoped templates to a "main function." User's actual mental model is simpler — a template is just a named, flat function list with per-function mode, no required parent/anchor field. Dropped `main_function_id` from the stored schema for that reason (see Recommended Approach).

### Approach B: Presets + call-graph auto-suggest (rejected)
Same as A, plus a new `CallGraph.function_root()` to auto-suggest a starting function list from a main function's direct callees, and proactive drift notifications wired into `AnalysisService`'s refresh callback.
Rejected: bigger surface area (touches `callgraph.py`/`funcview.py`, shared with the Routes tab) for a nice-to-have (auto-suggestion) the user didn't ask for. Auto-suggestion can be added later without changing the template schema from A.

### Approach C: Live-computed templates, no stored list (rejected)
Store only `{main_function_id, depth policy}` and recompute the armed set fresh from the call graph every time — "missing function" can't go stale because nothing is snapshotted.
Rejected: the user explicitly wants a **stored, editable list that gets applied as-is** ("when we add the template all the functions will be added to the trace as it is added to the template, if deep, if top accordingly") — a live-recomputed set would silently change membership on every code edit, which contradicts "as is."

## Recommended Approach

**Approach A, with the schema simplified per the user's own framing.**

**Data model** — `.cache/templates-{sha1(project_path)[:12]}.json`, same atomic-write/versioned pattern as `backend/analysis/service.py:260-295`:
```json
{
  "version": 1,
  "project_path": "...",
  "templates": [
    {
      "id": "tpl_...",
      "name": "checkout flow",
      "functions": [
        {"id": "app.checkout:process_order", "deep": true},
        {"id": "app.payments:charge_card", "deep": false}
      ],
      "created_at": "...",
      "updated_at": "..."
    }
  ]
}
```

**Backend — REST** (new routes alongside the existing `/viewer/terminal/selection*` family in `backend/api/viewer.py`):
- `GET /viewer/terminal/templates` — list templates; each function entry annotated live against the current catalog: `ok` / `missing` (+ up to 3 rename suggestions via the existing `difflib.get_close_matches` helper, lifted out of `mcp_server.py:145-151` into a shared util both REST and MCP call). Before the first AST scan completes (`state.scan_result` not yet populated), annotate every entry as `status: "unknown"` rather than `missing` — a startup race must never show a false missing badge.
- `POST /viewer/terminal/templates` — create from `{name, functions}`. Validation: `name` must be non-empty after trimming and unique (case-insensitive) among existing templates for this project — reject with 409 on a duplicate; `functions` must be a non-empty list of valid `{id: str, deep: bool}` entries (ids are not required to resolve against the current catalog at save time — a template can be authored for functions on a branch you haven't checked out yet).
- `PUT /viewer/terminal/templates/{id}` — rename and/or replace the function list (this is "edit"); same validation rules as create, applied to whichever fields are supplied.
- `DELETE /viewer/terminal/templates/{id}`.
- `POST /viewer/terminal/templates/{id}/apply` — resolves `functions` into the `[{"id","deep"}]` shape the selection endpoints already use, and calls the same `_update_selection` / `_push_selection` path (`viewer.py:197-215, 390-398`). Functions that don't resolve against the current catalog are skipped from what gets pushed to brain and surfaced as `unresolved`, exactly like a manual `arm_functions` call with a stale id — apply never partially-fails silently, it arms what it can and reports the rest.
- All CRUD + apply handlers on this store acquire a single per-project `asyncio.Lock` around their read-modify-write of the templates file, so a UI edit and a concurrent MCP `save_template`/`update_template` can't race and silently drop one write.

**Backend — MCP** (`backend/mcp_server.py`, sibling tools to the existing `arm_functions`):
- `list_templates()`
- `save_template(name, functions)` — `functions` uses the same `{"id","deep"}`-per-entry shape `get_armed()` already returns (`mcp_server.py:170-175`), **not** `arm_functions`'s input (`arm_functions(function_ids, deep=False)` applies one shared `deep` flag to a whole batch — it can't express "these 3 are deep, these 2 aren't" in one call). When the functions Claude wants to save were armed across multiple `arm_functions` calls with different `deep` values, call `get_armed()` first to recover the true per-function modes, then pass that list to `save_template`.
- `apply_template(id)`
- `update_template(id, name?, functions?)`
- `delete_template(id)`

This means Claude, mid-debugging-session, can call `arm_functions([...], deep=True)`, investigate, then call `get_armed()` and pass its result to `save_template("payment bug repro", [...])` — and you (or Claude, next time) can `apply_template(...)` to jump straight back into that exact instrumentation.

**Frontend** (`frontend/src/lib/store.ts`, `CatalogPane.tsx`, `CatalogModal.tsx`):
- `TerminalStore` gains `templates: Template[]`, `loadTemplates()`, `saveTemplate(name)` (captures current `selectedFunctions` + `functionModes`), `applyTemplate(id)`, `updateTemplate(id, ...)`, `deleteTemplate(id)`.
- `CatalogPane.tsx` gets a "Save as template" action next to the existing "Apply Changes" button, and a template picker (list of saved templates) — clicking one calls `applyTemplate()`, which replaces `selectedFunctions`/`functionModes` and runs the existing `applySelection()`.
- Missing functions inside a template reuse the exact `armed-error` badge/tooltip styling already in `CatalogPane.tsx:124-138`, plus a one-click "rename to X?" affordance sourced from the backend's suggestion list. Accepting a suggestion only stages the substitution in the open edit view — it takes effect (persists via `PUT .../templates/{id}`) only when the user explicitly saves, same as any other in-progress edit.
- The edit view is a **new, small component** — not a reuse of `CatalogModal.tsx` as-is. `CatalogModal.tsx`'s add/remove actions call `store.toggleFn`/`store.setDeep` directly against the live, global `selectedFunctions`/`functionModes` (the state that drives what's actually armed right now), so wiring it unmodified to a template editor would arm/disarm live tracing just by opening a saved template to look at it. The edit view instead holds its own local draft `{name, functions}` state (can reuse `CatalogModal`'s catalog-browsing/search UI as a picker, parameterized to add/remove against the local draft instead of the live store) and only touches the real armed state if the user clicks "Apply."

## Open Questions

- **Replace vs. merge on apply:** applying a template replaces the current arm-set (matching how `applySelection()` already behaves) rather than adding to it. Flag this if it turns out you want to layer a template on top of an existing manual selection — a "merge" mode could be added later without a schema change.
- **Per-tab vs. shared armed state:** `HUB.selection` is process-wide today (not per-browser-tab). Applying a template from one tab affects every connected dashboard. This is an existing property of the system, not something this feature changes — worth knowing if you ever have two Terminal tabs open at once.

## Success Criteria

- Save the current arm-selection as a named template in ≤2 clicks.
- Apply a saved template and have every function armed with the exact deep/shallow mode it was saved with, in one click.
- Edit an existing template (add/remove functions, toggle modes, rename) and re-save it.
- A template referencing a function that no longer exists shows a visible missing badge (reusing existing styling) instead of silently failing to arm it — with a rename suggestion when one is confidently found.
- Claude can list, create, apply, edit, and delete templates via the new MCP tools — verified by calling them directly against a running backend.

## Distribution Plan

Existing app, existing deployment — no separate distribution channel needed. This ships as part of the normal backend + frontend build.

7. Manual test pass:
   - Create a template → restart the backend → confirm it persisted.
   - Rename or delete a traced function in the target app's source → reload Terminal → confirm the missing badge and rename suggestion appear, and that accepting a suggestion only stages the change until saved.
   - Edit an existing template: add a function, remove one, toggle a mode, rename the template, save → confirm the stored file reflects exactly the new list.
   - Save a template with a mix of deep and shallow functions, apply it, and confirm each armed function's mode in `get_armed()`/the UI exactly matches what was saved (not all-deep or all-shallow).
   - Apply a template containing one deliberately-broken function id → confirm the other functions still arm and the broken one is reported as `unresolved`, not a hard failure.
   - Call the new MCP tools directly (`list_templates`, `save_template` using `get_armed()`'s output shape, `apply_template`, `update_template`, `delete_template`) to confirm Claude-side create/apply works.

## What I noticed about how you think

- You went straight to "a list saved somewhere, synced with live code" instead of a one-off convenience hack — and it turns out this codebase already has 80% of the infrastructure for exactly that (a JSON-cache pattern, a fuzzy-rename matcher sitting half-used in the MCP tool). You're pattern-matching to what's already there before you've even seen the code.
- You explicitly asked for this to work "in the mcp server request for the claude as well" — you're not just building a UI convenience, you're building a shared vocabulary between you and Claude for naming "the interesting functions in this flow." That's a different way to collaborate with an agent on your own code than most people reach for.

### R2-2 — completeness

**Problem**

> Validation rules stated only for REST create/update; MCP save_template/update_template don't mention enforcing the same rules.

**Remedy**

> State save_template/update_template enforce identical validation via the same TemplateStore logic, and specify the error shape on validation failure.

**Problem**

> PUT's name-uniqueness check doesn't say whether it excludes the template's own current name, so a no-op rename or case-only correction could be wrongly rejected.

**Remedy**

> State the uniqueness check on PUT excludes the template being edited.
